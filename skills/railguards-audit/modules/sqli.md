# SQL and NoSQL Injection

## R: Risk First
**Goal**: Prevent injection that grants unauthorized database access or modification.
**Risk**: Data breach, data tampering or deletion, authentication bypass, full database compromise.
**Context**: Applications using MySQL, PostgreSQL, SQL Server, Oracle, SQLite, MongoDB, DynamoDB, Elasticsearch and similar stores, including queries generated by LLMs.

## A: Attached Constraints
- ALWAYS use parameterized queries (prepared statements) for every value.
- NEVER concatenate or interpolate input into query strings.
- ALWAYS allowlist dynamic table names, column names and sort parameters.
- NEVER build dynamic SQL from input inside stored procedures.
- ALWAYS run the application with least-privilege database accounts.
- NEVER pass user-controlled objects straight into NoSQL query filters.
- NEVER execute SQL written by an LLM against a privileged connection without validation.

## I: Isolation
- **Trust boundaries**: the application/database boundary; the boundary between model-generated SQL and the database.
- **Untrusted inputs**: request data, stored data that originated from users (second-order injection), and LLM-generated query text.
- **Least privilege**: separate accounts per function; read-only accounts for read paths; text-to-SQL features use a read-only role scoped to approved views.

## L: Local Defaults

**When building queries**:
- Use placeholders (`?`, `:name`, `$1`, `@param`) and bind every value. The database must distinguish code from data regardless of content.
- Convert input to non-string types (int, bool, UUID) before use where possible.

**When identifiers must be dynamic**:
- Map user input to a fixed set of known identifiers: `ORDER_COLUMNS = {"date": "created_at", "total": "amount"}`.

**When using NoSQL**:
- Reject objects where scalars are expected (block `$ne`, `$gt`, `$where` injection); cast to string or use schema validation (Mongoose strict schemas, Pydantic).

**When offering text-to-SQL**:
- Execute on a read-only role against views; parse and allowlist statement types (`SELECT` only); enforce row limits and timeouts.

**When configuring access**:
- One account per application function with minimum permissions; errors never expose schema details.

## G: Generative Path Checks
1. Are all queries parameterized rather than string-built?
2. Are dynamic identifiers mapped through an allowlist?
3. Are stored procedures free of dynamic SQL built from input?
4. Are NoSQL filters built from typed, validated values?
5. Do application accounts follow least privilege?
6. Are database errors handled without leaking structure?
7. Are database connections encrypted and authenticated?
8. Is any LLM-generated SQL executed with a read-only, scoped role?

## U: Uncertainty Disclosure
- **Safe default**: treat any string-built query with a non-literal component as vulnerable until the component is proven constant.
- **Escalate when**: a raw query helper is shared widely and you cannot see all callers; report the helper with `medium` confidence and list the callers you verified.

## A: Auditability
- **Log**: query failures with a query identifier (not the full query with values), permission-denied errors, text-to-SQL statements rejected by the allowlist.
- **Never log**: bound parameter values that include credentials or PII.

## R: Review
1. Did a new raw query or ORM escape hatch (`raw()`, `extra()`, `text()`, `$queryRawUnsafe`) appear?
2. Did a new sort or filter parameter reach an identifier position?
3. Has the application account gained permissions it does not need?

**Core principle**: Never let input become query code. Bind every value, allowlist every identifier, and give the application only the database privileges it needs.

## S: Spend
- Runs in: `railguards-auditor-web`.
- Gate: recon found a database driver, ORM or query builder.
- Scanners first: Semgrep SQL injection rules.
- Read: grep for raw-query sinks (`execute(`, `query(`, `raw(`, `text(`, `$queryRawUnsafe`, `createQuery`, `find(` with request objects) and read only those call sites plus the source of each interpolated variable.
- Skip: ORM calls that use built-in parameterized methods (see the false-positive filter).
